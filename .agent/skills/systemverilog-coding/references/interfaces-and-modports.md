# Interfaces and Modports Reference — SystemVerilog

## What interfaces solve

Without interfaces, connecting a 10-signal bus between a producer and consumer requires
10 individual port declarations on each module and 10 connections at instantiation.
An interface bundles those signals into a single named object, with modports enforcing
direction constraints per role.

---

## Parameterized interface anatomy

```systemverilog
interface my_bus_if #(
    parameter int DATA_WIDTH = 32,
    parameter int ADDR_WIDTH = 16
) (
    input logic clk,
    input logic rst_n
);
    logic [DATA_WIDTH-1:0] data;
    logic [ADDR_WIDTH-1:0] addr;
    logic                  valid;
    logic                  ready;

    modport producer (
        input  clk, rst_n,
        output valid, data, addr,
        input  ready
    );

    modport consumer (
        input  clk, rst_n,
        input  valid, data, addr,
        output ready
    );
endinterface
```

Key points:
- Clock and reset are passed as module inputs to the interface — they are not
  internal signals generated by the interface.
- Modports **do not copy** signals; they add direction constraints on a view of the
  same signals.
- Parameterized interfaces require the parameter to be specified at instantiation.

---

## Instantiating a parameterized interface

```systemverilog
// In a testbench or top-level
my_bus_if #(.DATA_WIDTH(64), .ADDR_WIDTH(20)) u_bus (
    .clk(clk),
    .rst_n(rst_n)
);

producer_mod u_prod (.bus(u_bus.producer));
consumer_mod u_cons (.bus(u_bus.consumer));
```

The `.producer` and `.consumer` after the interface instance name select the modport view.

---

## Module ports using modports

```systemverilog
module producer_mod (
    my_bus_if.producer bus
);
    always_ff @(posedge bus.clk or negedge bus.rst_n) begin
        if (!bus.rst_n) begin
            bus.valid <= 1'b0;
            bus.data  <= '0;
        end else begin
            bus.valid <= 1'b1;
            bus.data  <= bus.data + 1;
        end
    end
endmodule
```

Alternatively, the modport can be selected at the instantiation site (as shown above)
rather than at the port declaration. Either is legal; selecting at declaration is
preferred for clarity and error checking.

## Clocking blocks

Clocking blocks define the timing of interface signals relative to the clock. They
are primarily for testbenches and formal tools; they are not synthesizable.

```systemverilog
interface axi_if (input logic clk);
    logic valid;
    logic ready;
    logic [31:0] data;

    // Testbench clocking block: drive 2ns before posedge, sample 1ns after
    clocking tb_cb @(posedge clk);
        default input #1ns output #2ns;
        output valid, data;
        input  ready;
    endclocking

    modport tb_mp (clocking tb_cb);
endinterface
```

Usage in a testbench:
```systemverilog
@(u_if.tb_cb);               // wait one clock
u_if.tb_cb.valid <= 1'b1;   // drive through clocking block
```

Gotchas:
- Clocking blocks are **not** synthesizable; keep them in TB-only interfaces or
  behind a `ifdef SIMULATION guard.
- Do not mix clocking-block driven signals with non-clocking-block drives on the
  same signal — simulation races result.

## Synthesis gotchas with interfaces

| Issue | Detail |
|---|---|
| Parameterized interfaces and some tools | Older Synopsys DC versions require interface parameters to be compile-time constants. Use `localparam` inside the interface where possible. |
| Interface arrays | `my_if u_bus[4]` (array of interfaces) is legal in IEEE 1800 but synthesis support is tool-dependent. Verify with your target tool before committing. |
| Modport direction enforcement | Synthesis tools enforce modport directions — an output in the modport assigned by an `always_comb` that reads it will error. |
| Interface in generate blocks | Instantiating interfaces inside `generate` blocks is legal but can confuse some tools. Label the generate block and ensure the interface instance name is unique. |
| No interface hierarchy in IEEE 1364 | Verilog-2001 does not support interfaces. If you need a Verilog-2001-compatible top level, flatten ports at that boundary. |

## Modport with tasks/functions (virtual interface)

Interfaces can include tasks and functions. These are used by testbenches via
virtual interfaces, which are handles to interface instances.

```systemverilog
interface drv_if (input logic clk);
    logic valid;
    logic [31:0] data;

    task automatic drive(input logic [31:0] d);
        @(posedge clk);
        valid <= 1'b1;
        data  <= d;
        @(posedge clk);
        valid <= 1'b0;
    endtask
endinterface
```

In a testbench class:
```systemverilog
class Driver;
    virtual drv_if vif;
    task run();
        vif.drive(32'hDEAD_BEEF);
    endtask
endclass
```

The `virtual` keyword on the handle type (`virtual drv_if`) allows runtime binding
to different interface instances.
